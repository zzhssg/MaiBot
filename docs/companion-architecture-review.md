# 陪伴机器人的双脑架构审查：麦麦（MaiBot）× DSH

> 审查对象：MaiBot + `dsh --profile acp` worker。**正式服 = mini（`100.74.18.68:8001`，`~/apps/maibot`）；测试服 = 本机 Mac（`127.0.0.1:8001`，`~/code/MaiBot`）。**
> 症状：回复有人味，但不干事、不解决问题。
> 结论：不是"结合得不够紧"，也不是模型不够强——**模型档位基本是对的，卡在每一跳的交接**：决定交给嘴的是一张 200 字的纸条，手交给决定的是一段被截断的正文。

## 0. 先给结论

1. **先对齐"哪台是线上"**：线上是 mini（`100.74.18.68:8001`，`~/apps/maibot`），`replyer` = `gemini-3.8-flash-high`；本机 Mac 只是开发实例（19:15 被重置成 DeepSeek）。我第一版审查读的是本机，结论作废。更要紧的是：线上 `worker.enabled=true` 但没有一条 `dsh_task` 日志——**这只手从没真正抬起来过**。
2. **结果在最后一跳被洗掉**：DSH 正文最多 8000 字（`src/agent/worker/delivery.py:10`）→ planner 必须压成 100–200 字 `chat_anlyze`，且 schema 明写"不要原文引用"（`src/maisaka/builtin_tool/reply.py:157`）→ replyer 只看到这段分析，看不到 DSH 结果。链接、文件名、数字在这一跳被明确要求丢掉。这是"不干事"的数学解释：**40× 压缩，最坏 200×**。
3. **桥只收正文**：`WorkerSession._collect` 只保留 `agent_message_chunk`（`src/agent/worker/session.py:108`）。而 DSH 的 ACP 实际会发 `agent_thought_chunk` / `tool_call` / `tool_call_update` / `plan`。进度、动作、产物引用、中途提问全部被丢掉——长任务在聊天里是黑箱。
4. **路由靠自觉，派活是一次性重承诺**：`dsh_task` 只对白名单可见，派不派全靠模型每轮即兴判断；而一次派活 = 900 秒超时 + 新开 ACP 会话 + 后台运行。模型天然回避重承诺，于是默认聊天。
5. **"事"没有状态**：没有任务账本注入上下文；每个任务新开会话（`src/agent/worker/pool.py:160`），追问靠手动传 `continue_from` 的 30 分钟 TTL；任务结束塞回一条内部消息，planner 重新决定说不说。用户问"那个怎么样了"，它可能根本不知道有这回事。
6. **线上已经跑通一次，但最后一跳丢事实**：19:50 打开 worker、20:02 补上 acp profile 后，第一条 `dsh_task`（dsh-1）成功返回，还带着 `head -n 3` 的证据。但最终回复把原文改成了「一个双语标签和一个居中的 div」——`chat_anlyze` 里明明有 `<a id="-双语--bilingual"></a>` 和 `<div align="center">`。这是 §3.2 的现场复现，见 §11。
7. **权限是静默全放行的**：worker 走 `dsh --profile acp`，该 profile 只有 `dsh-base` + `dsh-acp-app`，没有 desktop 那套 permission preset patch；而 `ACPConnection._server_request` 对每一个 `session/request_permission` 都直接选 `allow_once`（`src/agent/acp.py:209`），注释写着"电脑工作区已由用户启用自主执行"。也就是说：没有分级、没有确认、没有审计，**每一次工具调用都被自动授权**。一旦群白名单开了，等于把 shell 交给群里的人。

目标形态不是"让麦麦更能干"，而是：**麦麦当唯一的前台（嘴、耳朵、记忆、关系），DSH 当有状态的工头（规划、动手、验收），中间用"工作包 + 结构化回传 + 任务账本"连接。判断何时干活靠制度，不靠模型每轮即兴。**

## 1. 这篇文章真正值钱的是什么

多数人读到的是"三家组合"。真正可迁移的是三条：

**第一，模型是偏科的人，管理者的职责是"拆、派、验收、转述"。**
Gemini 好聊但粗心、harness 烂；GPT 严谨但没法沟通；Claude 够聊、够严谨、harness 最好，所以站中间。这条判断标准不是"谁最强"，是"谁最能把别人的产出变成我能信的结果"。

**第二，中间人必须同时具备可沟通性、主动性、严谨、好 harness——而现实中不存在这样的完美模型，所以要用制度补，而不是指望某个模型的天赋。**
文章里所有具体做法（CLAUDE.md 的先问清单、派活粒度、审查分两级、最多两轮）都是制度：把"判断"从模型的即兴变成可重复的流程。

**第三，也是最容易被忽略的一条：**
> "他纠正一次、审查退回一条，就在修它的同一个合并请求里把这一类拦住：能机械判断的写成检查，能改接口或目录、让错的写法写不出来的就改结构，都做不到才写进文字规则。"

你现在把"该派活"写在了工具描述里——这是第三档，最弱的一档。而 DSH 结果的丢失、路由的漏派，本来都可以做成第一档（确定性闸门、结构化字段、必填事实块）。

## 2. 一条消息现在的完整旅程

```
IM / WebUI 消息
  │
  ├─ 防抖 / 注意力 / 是否该说话（heart_flow, turn_trigger）
  │
  ├─ Planner  (4.1-flash)                  ← 决定：聊 / 干 / 沉默
  │     ├─ query_memory / tool_search / reply / wait
  │     ├─ dsh_task(brief)
  │     │      └─ WorkerPool ──► 新开 ACP 会话 ──► dsh --profile acp (flash)
  │     │                             └─ 只回传 agent_message_chunk
  │     │      └─ 结束：正文(≤8000字) 作为内部消息塞回聊天
  │     │
  │     └─ reply(chat_anlyze 100–200字, reply_style)   ← ①压缩点
  │
  └─ Replyer (4.0-pro)                     ← 只看到真实聊天 + 那段分析
        └─ 最终可见回复（"简短表达"时 1–2 句）          ← ②压缩点
```

两个真相：

- **Planner 看到的 DSH 结果，永远不会到达 Replyer。** Replyer 只接收"真实收发的 IM 消息"（`src/chat/replyer/maisaka_generator_base.py:670`）和 planner 给的 `chat_anlyze`。也就是说：干了什么、文件在哪、测试过没有，全靠 planner 用 100–200 字转述一次。
- **这条链上没有任何一处"验收"。** DSH 说做完了，planner 就信；planner 说做完了，replyer 就照着说。文章里"没过 GPT 审查进不了 CI"的那道闸，这里完全不存在。

## 3. 为什么"有人味但不干事"是结构问题，不是提示词问题

### 3.1 先把"哪台是线上"对齐：你聊的那台和我在读的那台不是同一台

| 机器 | 定位 | replyer | planner | worker 状态 |
|---|---|---|---|---|
| mini `100.74.18.68:8001` | **正式服（你每天聊的）** | `gemini-3.8-flash-high` | `deepseek-v4.1-flash` | `enabled=true`、`workspace=/Users/morty/code`；**20:02 首单 dsh-1 跑通（45s），但最终回复丢了原文** |
| 本机 Mac `127.0.0.1:8001` | **测试服（调试/自测）** | `deepseek-v4-pro`（19:15 被重置） | `deepseek-v4.1-flash` | 代码在、`enabled=false` |

证据：

- mini 的 `~/apps/maibot/config/model_config.toml:11` = `["gemini-3.8-flash-high"]`；日志里 Gemini 343 次、DeepSeek 4.1-flash 879 次。
- mini 的 `[agent.worker]` 是 19:50 写入的（`enabled=true`、workspace 指 `~/code`），20:02 之前 `logs/` 里没有任何 `dsh_task` / `agent.worker`——线上从没成功派出过；20:02 补上 acp profile 后跑通了第一条（§11）。
- mini 的 `~/.dsh/profiles/acp/cordis.patch.yml` 还是空的 `[]`：没有 provider/model 的 patch，`dsh --profile acp` 起来的会话大概率在 `session/new` 就报 "no API key for provider route"。本机 19:07 的部署记录踩的就是这个坑。

结论：

1. **线上那只见不到"手"**：Gemini 的嘴、DeepSeek 4.1-flash 的脑都在，worker 开关刚打开、一次没跑通。
2. **本机那只有代码没嘴**：19:15 的迁移把 Gemini 换成了 DeepSeek 默认值，`enabled=false`。
3. 20:02 之后情况变了：线上跑通了第一条，但回复没把事实带出来。**现在的问题不是"没接上"，是"接上了但最后一跳丢事实"。**

这也修正了我前两版的说法：第一版读的是本机（错），第二版说"线上是 DeepSeek"（也错，那是本机 19:15 之后的状态）。

### 3.2 最后一跳的压缩，是"不干事"的物理原因

`chat_anlyze` 的 schema 原文：

> "用一段话，约 100-200 字描述当前对话局面与查到的关键事实……**不写入长段原文**……**不要原文引用**，不评价回复价值、不写回复原因、不构想或指导如何回复。"

而 `dsh_worker_result.prompt` 又在说：

> "把结果里的链接、数字、文件名原样写进 chat_anlyze。"

**两条规则在打架**，而且 schema 是每次调用都在场、prompt 是事后补丁。模型会服从更具体、更靠近工具调用的 schema。这就是"文件在 …"这类回复的来源：不是它不想说，是它被要求别说。

### 3.3 桥丢掉的不是"锦上添花"，是"正在干活"这件事本身

ACP 的事件里本来有 `tool_call` / `tool_call_update` / `plan`，`_collect` 只收 `agent_message_chunk`。结果是：

- 没有进度：3 分钟的活在聊天里等于 3 分钟消失；
- 没有产物：截图、diff、生成的文件引用全部丢弃，只剩一句"改好了"；
- 没有中途提问：worker 想确认只能把"需要确认：…"埋进最终正文，等它跑完才被看到——这时候已经晚了。

这不是 DSH 没能力，是**桥把能力截断了**。

### 3.4 派活是一次性重承诺，而不是一段关系

一次 `dsh_task` 的成本：新开 ACP 连接 + 新 session + 冷启动 + 900 秒超时 + 后台排队。对模型来说，这是一个"要么全对要么全错"的重承诺；对用户来说，这是一次"说完就没了"的投递。

真正的陪伴式协作应该反过来：**低承诺地接住（"我看看"），高频率地反馈（"找到问题了"），确定地交付（"改好了，你试试"）。** 现在只有最后一帧，而且大概率还是模糊的。

### 3.5 记忆和工程面是分裂的

`A_memorix` 的记忆、关系、表达在麦麦这边；DSH 只知道工作目录和一句 brief。于是：

- "把上次说的那个东西做完"——麦麦要凭记忆复述给 DSH，细节一定丢；
- DSH 干完的结论——回不到麦麦的长期记忆里，下次还得重新找；
- DSH 的产物（文件、URL）——没有落进记忆，也没有落进聊天。

这不是 prompt 能修的，缺的是一份**共享账本**。

### 3.6 一个容易被忽略的事实：现在这份配置里，worker 是关的

`agent.worker.enabled = false`、`workspace = ""`。如果"实测"是在这个状态下做的，那测出来的不是架构问题，是没接上。建议先花五分钟确认：工具到底有没有出现在 planner 的工具列表里、`dsh_status` 能不能返回、一次真实派单的日志长什么样。**诊断要建立在"它确实在跑"之上，否则会把配置问题误判成设计问题。**

### 3.7 权限被静默短路了

`ACPConnection._server_request` 处理 `session/request_permission` 时，永远挑 `allow_once`（`src/agent/acp.py:209`），注释的理由是"电脑工作区已由用户启用自主执行"。结果是 DSH 那套审批机制在桥这里直接失效：没有分级、没有确认、没有审计，每一次工具调用都是自动授权。acp profile 又只有 `dsh-base` + `dsh-acp-app`，没有 desktop 的 permission preset patch 可以兜底。

这不是"以后再说"的问题：只要有人能把一句话送进这个聊天，他就能让 DSH 在 `workspace` 里跑任意命令。当前靠"主人私聊才可见"挡着，但白名单一开就是另一回事。

## 4. 目标架构：前台 / 工头 / 账本

```
                    ┌──────────────────────────────┐
   用户 ◄───────────│  前台：麦麦（唯一说话的人）   │
                    │  耳朵：理解、情绪、记忆召回    │
                    │  嘴：所有面向用户的话          │
                    └───────┬──────────────▲───────┘
                            │ 工作包        │ 进度 / 问题 / 结果
                            ▼              │
                    ┌──────────────────────┴───────┐
                    │  工头：DSH 长驻会话            │
                    │  规划、工具、subagent、验收     │
                    │  只产出结构化事件，不说话       │
                    └───────┬──────────────────────┘
                            │ 读写
                    ┌───────▼──────────────────────┐
                    │  账本：open threads / 任务状态  │
                    │  最近结果 / 常驻偏好 / 产物索引 │
                    └──────────────────────────────┘
```

**前台红线**（保持现有"worker 不说话"的正确直觉）：

- 所有面向用户的话只从前台出，包括接单、进度、交付、失败；
- 前台不再直接执行业务工具，只保留记忆、表情、轻量查询；
- 前台不猜结果：没有工头回报的事实，不许说"好了"。

**工头红线**：

- 有状态：按用户/项目长驻，而不是按任务新开；
- 自己验收：交付必须带"做了什么 / 怎么验证的 / 没做完什么"；
- 只产出三类事件：`progress`（一句话）、`question`（要用户拍板）、`result`（结构化）；
- 不直接对 IM 说话（这条你们已经做对了，保留）。

**账本**是这套架构里最便宜、收益最大的一块。它解决三件事：追问有指代、进度可见、失败可解释。

一次派活的正确时序：

```
t=0s   用户："把那个脚本改成支持 --dry-run"
t=1s   前台："行，我看看"                     ← 先接住，人味在这一拍
t=2s   工头：接单（用户看不见）
t=40s  工头：progress "找到问题了，参数是写死的，我改成读取环境变量"
t=90s  工头：result  done / 改了 2 个文件 / 验证：--dry-run 输出符合预期
t=91s  前台："改好了，dry-run 能跑，参数从环境变量读。你试试？"
```

注意 t=1s 那一拍：**它不是礼貌，是设计。** 先回人话再派活，用户永远不会觉得被冷落；而如果先判断再回，派活的握手延迟会直接变成回复延迟。MaiBot 现成的 `after_reply=continue`（`src/maisaka/builtin_tool/reply.py:142`）正好支持这个顺序：`reply(接单) → dsh_task → wait`。

## 5. 判断制度：什么时候干活，什么时候聊天

### 5.1 立场

**默认聊天，干活要理由。** 陪伴机器人的默认状态是"在场"，不是"待命"。把默认反过来，它就会变成一个会撒娇的任务机器人——那才是最糟的结果。

### 5.2 四问

每轮只问四个问题，按顺序短路：

1. **有没有交付物？**（文件、改动、查询结果、外部动作、需要多步才能得出的结论）
   → 没有 = 聊天，结束。
2. **用户在求助，还是在倾诉？**
   → 倾诉/分享/吐槽/称呼/情绪 = 先接住，最多末尾轻问一句"要不要我去弄"，**不派活**。
3. **我自己一两步能不能做完？**（记忆、一句搜索、读一条消息）
   → 能 = 自己做，不派活。派活的沟通成本通常大于活本身。
4. **对象和验收说清楚了吗？**
   → 清楚 = 派；不清楚 = 问一句，不猜。

### 5.3 六条规则（优先级从高到低）

| # | 规则 | 触发 | 动作 |
|---|---|---|---|
| R1 | **粘性** | 有 open thread，且这句是接续（"继续/改一下/那个/还是刚才"） | 直接进慢循环，不重新分类 |
| R2 | **显式** | `/work`、"帮我改"、"去跑一下"、"做完告诉我" | 派 |
| R3 | **能力缺口** | 前台需要但做不到（PDF、命令行、改代码、多步调研） | 派，而不是编 |
| R4 | **情绪红线** | 称呼、撒娇、吐槽、深夜倾诉、"你在吗" | 只聊；**禁止派活** |
| R5 | **模糊** | 有交付物但对象不明 | 一句话澄清，默认聊 |
| R6 | **失败** | 工头 failed/timeout | 说清卡点 + 两个选择，不重试不静默 |

R1 是这套制度里最关键的：**一旦开了 thread，判断就结束了。** 人不会每句话都重新决定"要不要帮朋友"，陪伴机器人也不该。

### 5.4 决策表

| 用户说 | 判断 | 前台 | 后台 |
|---|---|---|---|
| "今天好累" | 聊 | 接住情绪 | 无 |
| "帮我看看这个 PDF" | 派（能力缺口） | "发我，我看完告诉你" | 提取 + 摘要 |
| "上次那个 bug 修了吗" | 查账本 | 直接答（在跑/已完成/没这回事） | 无 |
| "把 X 改成支持 Y" | 派（交付物明确） | "行，改完说" | 工作包含验收 |
| "你觉得我该换工作吗" | 聊（决策/情绪） | 聊，可问一句 | 不派 |
| "随便聊聊" | 聊 | 聊 | **禁止派** |
| 群里 @ 它"跑个测试" | 不派（权限） | "这个得私下说" | 无 |

### 5.5 这套制度的边界

- **宁可问一句，不要猜。** 猜错的代价是用户要收拾残局，问一句的代价是半秒。
- **情绪时刻不问"要不要帮忙"，只在最后轻轻带一句。** 否则陪伴感立刻变成客服感。
- **同一个 thread 里不重复确认。** "改一下"就是继续，不要再问"你是说上次那个吗"。

三个改法，按性价比排序：
- 给 `reply` 工具加 `must_include: string[]`（链接/数字/路径/文件名），让它进入 reply 模板（`_build_reply_template_context`），模板规定"这些必须原样出现"；
- 给 `reply_style` 增加一个"交付"档：允许链接、路径、列表、步骤，明确"不用短句、不用寒暄"。聊天用聊天模板，交付用交付模板，别让工程结果挤在"1–2 句"里；
- 或者让 replyer 直接看到工头的结构化结果摘要（只读、不可改写）。
同时删掉 `chat_anlyze` schema 里"不要原文引用"的表述，或把它限定为"不要整段粘贴过程"。
验收：派"读出 README 第 3 行并贴出来"，回复必须出现原文；派"查三个新闻并列链接"，三个链接必须齐全。

**P0-3 接 ACP 事件做进度心跳**
`session.py` 的 `_collect` 增加 `tool_call` / `tool_call_update` / `plan` 分支，转成一句话进度（"正在读文件""在跑测试"），走内部消息。不要暴露原始工具名和参数。
验收：>60 秒的任务至少 1 条进度，且读起来像人话。

**P0-4 任务账本注入上下文**
每轮给 planner 一段："进行中：X（已 2 分钟）/ 最近结果：Y / 未完成：Z"。用户问"怎么样了"必须能答。
验收：跑一个 3 分钟任务，中途问"到哪了"，回答必须准确。

### P1：让它像一个人在干活

**P1-1 嘴的 A/B：Gemini vs DeepSeek**
线上现在 replyer 是 `gemini-3.8-flash-high`（34.3 万次调用里 343 次），planner 是 `deepseek-v4.1-flash`。用同一批真实聊天记录跑两份，只看"人味"（口语化、短句、不写说明书、情绪贴合、不油腻）和事实保真（链接/数字/文件名是否原样保留），不看跑分。
- Gemini 更好 → 留着，别再为"统一模型"折腾；贵一点但那是产品的核心资产。
- DeepSeek 不差 → 省一大笔，少一个供应商。
验收：20 条真实对话盲评 + 10 条含链接/数字的事实保真测试。

**P1-2 长驻工头会话**
按用户（或项目）保留一个 DSH 会话，而不是每个任务新开；`continue_from` 从手动变成粘性默认。跨任务连续性靠它，而不是靠 30 分钟 TTL。
验收："上次那个文件"能直接指代，不需要用户重复路径。

**P1-3 产物回传**
工头结果里的文件路径、URL、截图，前台用附件/图片发出去，而不是"文件在 …"。
验收：生成一张图，聊天里直接收到图。

### P2：关系与工程的融合

**P2-1 记忆双向**
工头完成后，把"事实"（不是过程）写回 `A_memorix`：做了什么、在哪、结论是什么。前台派活时从记忆取"已知事实"塞进工作包。
验收：一周后问"上次改的那个脚本在哪"，能答对。

**P2-2 反问通道**
工头需要拍板时，以麦麦的口吻反问用户（走 `question` 事件），而不是把问题埋在最终正文里。
验收：故意给一个缺参数的活，用户应当被问到，而不是收到一份猜出来的结果。

**P2-3 权限分级**
现在 `src/agent/acp.py:209` 对所有权限请求都选 `allow_once`，等于把 DSH 的审批机制整个短路了。改成按类别决策：读（放行）/ 写工作区内（放行或记账）/ 执行命令（按白名单）/ 外部副作用（必须问）。群聊默认只读。高风险动作走"主人确认"卡片。
验收：群里发"删掉那个目录"，必须被拒绝并说明原因；工作区外写入必须被拦。

**P2-4 交付闸门**
工头 result 必须含"做了什么 / 怎么验证的 / 没做完什么"三段；缺验证的，前台不许说"好了"。
验收：故意让工头失败一次，回复必须说清卡在哪 + 两个选择，且 0 次"已完成"。

## 7. 与文章的对照

| 文章 | 你的系统 | 差距 |
|---|---|---|
| Gemini：会聊、点子多、粗心、harness 烂 | replyer（4.0-pro） | 会说话，但被 200 字纸条限制 |
| GPT：严谨、能干活、难沟通 | worker（4.1-flash） | 被降级成一个函数，只递纸条 |
| Claude：中间人，听懂、拆解、验收、转述 | **缺位** | 没有"能验收别人产出"的那一层 |
| CLAUDE.md 的先问清单、派活粒度 | 工具描述 + prompt | 文字规则，第三档 |
| 审查分两级、最多两轮、CI 前必过 | 无 | 没有任何交付闸门 |
| 纠正一次就写成检查/结构 | 无 | 路由和保真全靠模型自觉 |

最值得抄的不是"三家组合"，是**"把纠正变成检查"**。你已经被"不干事"纠正过一次了，正确反应不是再改一版工具描述，而是把"该派的必须派、派出去的事实必须回来"做成确定性的东西。

## 8. 不建议做的四件事

1. **给麦麦塞更多 DSH 工具。** 你们自己的文档已经写对了："弱 Planner 拿强工具只会把错误链拉长。"问题不在工具数量，在交接契约。
2. **让 DSH 直接说话。** 一旦它开口，人味就没了，而且会出现两个声音。保持"只有一个说话的人"。
3. **把 planner 做成全能 agent。** 它的职责是判断和转述，不是执行。职责一旦扩张，延迟和错误率都会上去。
4. **现在迁移到 DSH 原生（人设卡 + IM 插件）。** 你们已经试过 IM 预设并在 11-23 移除了；MaiBot 的平台适配、A_Memorix、表达学习、桌宠是多年资产。双脑协议是当前性价比最高的路；等 DSH 侧 IM/人格生态成熟再评估。

## 11. 首次线上验证（2026-11-23 20:02）

**准备**：给 mini 的 `~/.dsh/profiles/acp/cordis.patch.yml` 补上 `apikl` provider + `deepseek-v4.1-flash`（原文件是空 `[]`，备份为 `cordis.patch.yml.bak-20261123-195748`）。用 `dsh --profile acp --dump-config` 确认 `acp.provider=apikl`。直接跑 ACP 冒烟：`initialize → session/new → session/prompt`，返回 `end_turn` + "ACP OK"。

**派单**：通过 WebUI 的内部聊天发 `/work 读一下 .../README.md 的前 3 行，把原文贴回来`。

**时间线**（`tool_records`）：

| 时间 | 工具 | 说明 |
|---|---|---|
| 20:02:01 | `dsh_task` | brief 写明了"逐字返回原文、失败说明原因、不要修改文件" |
| 20:02:21 | `reply` | "扔给后台去读了，等跑出来我叫你" |
| 20:02:46 | `reply` | 结果转述 |

**worker 返回**（planner 收到的 `chat_anlyze`）：

> 后台任务 dsh-1 已 done，读取了 README 的前 3 行。第 1 行是 `<a id="-双语--bilingual"></a>`，第 2 行是空行，第 3 行是 `<div align="center">`。验证依据：`head -n 3` 输出即为这三行，`ls -l` 显示文件 15353 字节……

**用户实际收到**：

> 跑出来了，前三行其实没啥内容
> 就一个双语标签和一个居中的 div
> 中间还空了一行

**结论**：

1. 手是好的：ACP 握手、session、prompt、结果回传、证据意识（`head -n 3` / `ls -l`）全都对。
2. 最后一跳是坏的：事实在 `chat_anlyze` 里，但经过 replyer 的"简短/口语化"约束后被改写成了描述。用户明确要"原文"，仍然没拿到。这正是 P0-3 要修的东西，现在有了可复现的验收用例。
3. 附带发现：内部聊天会话带着旧上下文，机器人先回了一句上一次测试的暗号（PURPLE-913），说明 WebUI 内部聊天是**长会话复用**的。验收时必须每次新开会话，或先清上下文，否则测出来的不是本轮行为。

## 12. 修复与复验（2026-11-23 20:15）

**改了什么**

1. `reply` 工具新增 `must_include: string[]`：本次回复必须原样出现的事实清单。
2. `reply_style` 新增「交付」档：允许分点、链接、路径、数字、命令输出，明确不用寒暄。
3. `chat_anlyze` 删掉「不要原文引用」，改成「关键事实另填 must_include」——原来的两条规则不再打架。
4. 回复模板新增 `{must_include_block}`（中/英/日 × 私聊/群聊/补充/ mai_replier，共 18 个），空清单时不渲染。
5. `dsh_worker_result.prompt` 三语同步：要求 planner 把链接/数字/路径/文件名/命令输出逐条填进 `must_include`，结果类回复用「交付」档。
6. 新增守卫测试 `pytests/maisaka/test_reply_must_include.py`（4 条），`pytests/maisaka` 全量 342 通过。

**怎么验的**

部署到 mini、重启后，用新会话发同一类任务：`/work 读取 accept-note.txt，把第一行原样贴回来`。

planner 实际调用（`tool_records` #244）：

```
reply_style: 简短表达
must_include: ["ORANGE-204", "BLUE-731 验收暗号：请原样返回这一行"]
```

最终回复里出现了 `BLUE-731 验收暗号：请原样返回这一行`，逐字一致。

**前后对照**

| | 修复前（20:02） | 修复后（20:15） |
|---|---|---|
| 用户要的 | README 前 3 行原文 | accept-note 第一行原文 |
| 最终回复 | 「一个双语标签和一个居中的 div」 | 「BLUE-731 验收暗号：请原样返回这一行」 |
| 事实位置 | 只在 chat_anlyze | chat_anlyze + must_include |

**结论**：事实保真与回复风格已经解耦——planner 仍可能选「简短表达」，但 `must_include` 的内容不会因为风格被压掉。下一步是让 planner 在纯交付场景主动选「交付」档，以及把进度事件接上（P0-3/P0-4 之后的 P1）。
